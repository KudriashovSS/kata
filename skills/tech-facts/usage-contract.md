# Контракт использования памяти фактов

Этот файл — **режим использования**: у проекта уже есть база технических фактов, и агент решает
обычные задачи разработки рядом с ней. **Ты работаешь автономно**: человека в сессии нет, спросить
некого. Всё сомнительное — не эскалация, а факт со статусом `candidate` и заполненным `question`;
его разберёт сессия эволюции или человек в UI. Глобальную правку памяти внутри задачи не делаешь:
трогаешь только то, что задача реально задела. Он самодостаточен: его инжектит хук в начале сессии и он же
кладётся в standing instructions инстанса (`xmemcli instance instructions <id> "<текст>"`).
Строительство базы — не здесь, оно в [SKILL.md](SKILL.md); модель факта и адаптеры —
в [memory-protocol.md](memory-protocol.md).

## Правила, которые не обсуждаются

1. **Факт без evidence не существует** — минимум один `файл:строка`, коммит или конфиг.
2. **Код прав, память — нет.** Расхождение → факт `stale` + новый `candidate`, вслух человеку.
3. **Ничего не удаляется** — только смена статуса со `status_reason` (+`superseded_by`).
4. **Пишешь `structured_mutations`-батчем**, не прозой ([почему](memory-protocol.md#2-запись--только-structured_mutations)).
5. **След задачи — один объект `Task`** со связями `used_facts` (что уехало в контекст) и
   `produced_facts` (что создал/заstale-ил), связи — **только по `fact_id`**, не прозой. Больше
   ничего не журналируешь: сколько токенов, сколько тул-колов и что было в контексте, пишет
   раннер прогона, а не ты.

## Цикл задачи

**U1 · Перед задачей.** Стартовый пакет памяти приезжает сам — его инжектит хук
(`xmemcli context --text`, инстанс привязан `binding add --tier autoload`). Мало для задачи —
дотягивай точечно: определи затронутые сущности и достань релевантные `active`-факты
(`xmemcli read ... --scope`, +`human_notes`). Читаются только `active`. → задача.

**U2 · Во время.** Факт разошёлся с кодом → правило «код прав»: `stale` + новый `candidate`,
одной мутацией, по ходу дела. Не копи правки на конец сессии и не переписывай соседние факты
«заодно» — то, что задача не трогала, идёт в эволюцию.

**U3 · После задачи.** Прогоняешь запись через гейт новизны (ниже). Реальность изменилась
(новое событие/зависимость/endpoint/инвариант) → новые `candidate`-факты (уверенные —
auto_approve), устаревшие → `stale` c `superseded_by`. Наступил на грабли → факт `gotcha`
(только как гипотеза). Одним батчем: мутации фактов + объект `Task` со связями. Сайт запущен —
перегенерируй затронутые страницы. Если сессия интерактивная и человек рядом — покажи дифф памяти
(≤10 строк в чат, больше — `push review` только с изменёнными фактами); в автономном прогоне
ничего не спрашиваешь.

**Что считается уроком.** Не только «в системе появился endpoint», но и результат собственной
работы: сборка упала на X, тест Y поймал регресс, проверка репозитория потребовала Z. Такой урок —
`gotcha`-факт с evidence на лог или дифф. Это единственный источник фактов, которого нет у
реверс-инжиниринга кода, — не теряй его.

## Гейт новизны: что писать и каким путём

Дёшево и детерминированно решай очевидное, к модели ходи только за спорным.

| Случай | Что делать |
| --- | --- |
| Ключ существует, содержание то же | **noop** — не пишем ничего |
| Изменение видно из диффа (endpoint, зависимость, событие, инвариант) | **`structured_mutations`** — create/update по явному ключу |
| Факт противоречит существующему | `update` проигравшего → `stale` + `superseded_by`; неразрешимое кодом — `candidate` с `question`, разбор в эволюции |
| «Что-то поменялось, но непонятно что» | текстовый `write` **только** с `--scope Type:key` — запись не сможет создать ничего за пределами привязанных объектов |
| Массовая переработка памяти | не в этой сессии — вынеси в эволюцию (E) |

Порог входа в память: факт должен пережить следующую задачу. Наблюдение, верное только для этого
диффа, — не факт.

## E · Эволюция памяти

Отдельной сессией между задачами или по cron, **никогда внутри задачи**: дедупликация, снятие
протухших, схлопывание шума, предложение новых типов фактов под накопившиеся `gotchas`/вопросы,
перегенерация сайта. Все изменения — через candidate/review-цикл, крупные — с ревью человека.

Здесь же разбирается очередь предложений схемы, которую xmemory копит **из read-трафика** — что у
памяти спрашивали и чего ей не хватило:

```bash
xmemcli schema suggestions review <instance_id>
xmemcli schema suggestions decide <instance_id> ...    # accept / reject / defer
xmemcli schema suggestions apply  <instance_id>        # применяется миграцией
```

Итог сессии — батч мутаций с явными id и короткий отчёт человеку.

## Как это запускается (хуки)

Механику и её ограничения см. в [../../dataset/README.md](../../dataset/README.md).
Коротко: чтение — **SessionStart** (stdout хука уезжает в контекст), запись — **Stop**
(единственный хук, который умеет вернуть агента в работу), **SessionEnd не использовать**
(его вывод игнорируется, а бюджет — 1.5 секунды на все хуки).
