# Протокол UI: сервер, стадии, форматы данных

UI — **одно приложение на одном порте** (default `4747`, env `TECHFACTS_PORT`). Агент не пишет
HTML: он кладёт JSON в рабочий каталог и переключает стадию; шелл (`ui/`) рендерит.

**Стадии не сменяют друг друга — они копятся.** Слева всегда сайдбар: «Срезы» (шаг 1), порции
ревью (шаг 2, по одной на срез, извлекаются параллельно), «Эксплорер» (шаг 3). Человек ходит
между разделами сам, в любом порядке и в любой момент — включая возврат на выбор срезов.
`state.stage` — не запрет, а подсказка «агент сейчас ждёт вот здесь»: пока человек никуда не
уходил сам, UI следует за агентом; как только он выбрал раздел, его оттуда не выдёргивают.
Маршрут в адресе: `#/picker`, `#/review/<батч>`, `#/explore/<страница>/<факт>`.

Обратная связь — **блокирующая**: агент запускает `await` и ждёт решения человека из браузера
(паттерн plannotator: сервер держит решение, агент забирает и продолжает). Решений может прийти
несколько подряд и не по порядку — человек ревьюит порции в удобной ему последовательности.

## Рабочий каталог (workdir)

Всегда во временной директории, **не в репозитории пользователя** (источник истины — xmemory;
локальные файлы — только витрина и транспорт): `${TMPDIR}/tech-facts/<slug-проекта>/`.

```
workdir/
  state.json        # {"stage":"picker|review|explore","project":"...","seq":3,"updated_at":"..."}
  picker.json       # payload раздела «Срезы»
  review.json       # все порции ревью (batches[]), дописывается по мере извлечения
  site/
    site.json       # конфиг сайта: страницы и блоки
    facts.json      # все факты (мини-ядро + свободные поля)
    entities.json   # опционально
  decisions.jsonl   # append-only: решения человека (пишет сервер)
  .ack              # курсор await (байтовое смещение прочитанного)
  .await.lock       # pid ждущего await; второй параллельный await падает, а не висит
```

## CLI (`scripts/server.mjs`, zero-dep, Node ≥ 18)

```bash
node scripts/server.mjs serve --workdir <dir> [--port 4747] [--open]   # сервер, форграунд
node scripts/server.mjs push <stage> --workdir <dir>                   # переключить стадию
node scripts/server.mjs await --workdir <dir> [--stage review] [--timeout 540]
node scripts/server.mjs status --workdir <dir>                        # health/stage/URL, exit 1 если сервер не поднят
node scripts/server.mjs export --workdir <dir> [--out page.html]      # самодостаточный read-only эксплорер
```

- `serve` — агент запускает в бэкграунде один раз за сессию. Повторный запуск при живом сервере
  на том же workdir — мягкий exit 0 с подсказкой «уже работает». Порт занят чужим процессом —
  внятная ошибка с советом `TECHFACTS_PORT`.
- `push` — валидирует payload, инкрементит `seq`, обновляет `state.json`. Сервер замечает
  изменение (fs-watch + poll-фоллбек 1с) и шлёт SSE. Валидация трогает **только мини-ядро**
  (факт без `id`/`statement`/`evidence`, срез без `id`/`title`, дубли, пустой `pages[]`) — это
  железные правила скилла, их нарушение роняет `push` со списком виноватых id. Схема фактов,
  набор срезов, любые дополнительные поля — не его дело: агент проектирует их свободно.
  Косметика (`statement` > 200, `summary` > 80, `recommended` > 3, нет `art`, незнакомый `status`)
  печатается предупреждением и push не блокирует. Аварийная дверь — `--force`.
- `await` — блокируется до **новой** записи в `decisions.jsonl` (после `.ack`), печатает её JSON
  в stdout, сдвигает `.ack`. Таймаут (default 540с — меньше лимита Bash-тула) → exit 3 и
  `{"timeout":true}`; агент просто перезапускает `await` — решение не теряется, курсор не сдвинут.
  Работает чисто по файлам: падение/рестарт сервера решений не теряет.
  **Один `await` на workdir.** Второй параллельный падает с exit 4 и внятным сообщением: они
  делят курсор `.ack`, и раньше второй молча зависал, пока первый уносил решение. Лок —
  `.await.lock` с pid, от умершего процесса подбирается сам.
  **В параллельном режиме зови `await` без `--stage`** и разбирай пришедшее по `type`: решения по
  разным порциям и правки состава срезов идут вперемешку. `--stage` — строгий FIFO: чужую запись
  он не проглатывает, а упирается в неё и отдаёт таймаут (ничего не теряется, но и не приходит —
  значит впереди очереди лежит решение другого типа).
- **Практика фоновых запусков.** Путь к `server.mjs` указывай **абсолютным**: у фоновой команды своя
  рабочая директория, и относительный `node scripts/server.mjs` отвалится на первом же вызове после
  `serve`. Дефолтный таймаут `await` (540с) подобран под лимит Bash-тула в форграунде — запуская
  `await` в фоне, ставь `--timeout 3600`: реже будишь человека сообщениями «ожидание переподнято».
- `export` — собирает один HTML-файл: шелл + вшитые данные `site/` (стадия explore, read-only,
  без решений). Для пересылки коллеге без сервера. **Для Artifacts — `--fragment`**: тот же
  контент без `<!doctype>/<html>/<head>/<body>`, ровно то, что принимает Artifact-тул (руками
  резать не надо; внутри вендоренного mermaid встречается строка `</body>`, наивный regex рвёт
  файл пополам — команда режет по `lastIndexOf`).

## HTTP API (сервер ↔ браузер)

- `GET /` и статика → `ui/` (шелл), `GET /api/health` → `{ok,stage,workdir}`.
- `GET /api/state` → `{state, payload, available}`. `payload` — файл текущей стадии;
  `available: {picker,review,site}` — что вообще есть в workdir (по нему строится сайдбар).
- `GET /api/file/<name>` → JSON из workdir (`facts.json`, `entities.json`…). Только чтение,
  только внутри workdir. Разделы UI читают свои payload'ы отсюда независимо от `state.stage`.
- `GET /api/decisions` → массив уже принятых решений из `decisions.jsonl`. По нему UI помнит,
  что отправлено (переживает перезагрузку страницы), и показывает, что ещё можно изменить.
- `GET /api/events` → SSE: событие `state` при любом изменении workdir (браузер перезапрашивает
  `/api/state`), `ping` каждые 25с.
- `POST /api/decision` `{stage,type,data}` → сервер добавляет `{seq,at}` и дописывает строку в
  `decisions.jsonl`. UI после отправки показывает состояние «улетело агенту» и блокирует
  повторную отправку той же формы (агент пришлёт следующую стадию).

## Payload стадий

### `picker.json` — лендинг выбора срезов

Первый экран решает судьбу всего процесса: он должен **читаться за 15 секунд**, а не изучаться.
Поэтому на карточке видно только картинку, название и одну строку сути; всё длинное — под
«подробнее».

```json
{
  "project": "services-platform",
  "intro": "Contract-first .NET монолит: 5 модулей, in-process события, PostgreSQL.",
  "auto_approve": "high",
  "slices": [{
    "id": "event-graph",
    "title": "Граф событий",
    "summary": "14 in-process событий через IEventBus, брокера нет",
    "art": "<svg viewBox=\"0 0 320 120\">…</svg>",
    "stars": 4,
    "cost": "S",
    "recommended": true,
    "found": "14 in-process событий через IEventBus в BuildingBlocks/, внешнего брокера нет",
    "value": "Агент без этого среза забывает уведомить консюмеров",
    "auto_note": "извлекается автоматически; семантика доставки — с валидацией"
  }]
}
```

Необязательный блок `memory` рядом с `intro` объявляет, куда ляжет память:

```json
"memory": {
  "backend": "local",
  "title": "Память сохраняется локально",
  "note": "xmemory недоступен: креды .xmemrc.json не найдены",
  "location": "~/.tech-facts/services-platform"
}
```
`backend: "xmemory"` — полоса не показывается; любое другое значение — шелл держит жёлтую полосу
на **каждом** экране: человек должен видеть, что память локальная, а не узнавать об этом потом.
Режим выбирается на разведке (B1), не после ревью.

Бюджеты текста (шелл не обрезает — врать не будет, но карточка поедет): `intro` ≤ 2 предложения,
`summary` ≤ 80 символов и без точки в конце, `title` ≤ 30. `found` / `value` / `auto_note` живут
в «подробнее» — там можно подробно.

`stars` (1–5) — автоматизируемость из fact-catalog, пересчитанная разведкой под этот репозиторий;
подпись рядом со звёздами шелл ставит сам. Карточки со `stars ≤ 2` помечаются «гипотеза —
потребует вашей валидации».

**`recommended` — максимум у трёх срезов.** Шелл отмечает галочкой только рекомендованные (и не
больше трёх, даже если агент отметил больше) и поднимает их наверх сетки. Выбор из трёх — решение,
выбор из восьми — работа; остальные срезы остаются рядом и включаются одним кликом.

**`art` — иллюстрация среза, которую агент рисует сам.** Это не иконка из набора: что нарисовать —
свобода агента, шелл сюжет не диктует и запасной картинки не подставляет (нет `art` — карточка
живёт без неё). Требования только технические: инлайновый `<svg>` с `viewBox` (пропорции ~16:6,
удобно `0 0 320 120`), цвета — `currentColor` и токены (`var(--primary)`, `var(--accent)`,
`var(--border)`, `var(--danger)`), чтобы картинка сама переезжала в тёмную тему; никаких внешних
ссылок, `<script>`, `<image>` и обработчиков — шелл их вырезает при рендере.

Решение: `{"stage":"picker","type":"picker","data":{"selected":["event-graph"],"auto_approve":"high","comment":""}}`

**Состав срезов можно менять после отправки.** Человек возвращается на «Срезы» в любой момент,
щёлкает карточки и присылает правку — это отдельное решение:

```json
{"stage":"picker","type":"picker_amend","data":{
  "selected": ["event-graph","data-ownership","api-contracts"],
  "added": ["api-contracts"], "removed": ["module-graph"], "comment": ""
}}
```
Агент обязан его отработать: `added` — доизвлечь и прислать новой порцией ревью, `removed` —
остановить извлечение и не сохранять срез в память (уже сохранённое — `stale/rejected`, вслух).

### `review.json` — порции ревью (срезы извлекаются параллельно)

Один файл держит **все** порции: агент дописывает батч, как только срез готов, и делает
`push review`. Человек ревьюит их в любом порядке, переключаясь в сайдбаре, — блокирующей
очереди «один срез за раз» больше нет.

```json
{
  "project": "services-platform",
  "batches": [{
    "batch": "event-graph",
    "title": "Граф событий",
    "status": "ready",
    "note": "12 фактов авто-подтверждены (high + evidence), 6 ждут решения",
    "diagram": {"mermaid": "flowchart LR\n  Orders -- produces --> order_created[order.created]"},
    "facts": [{
      "id": "fact:eg-0001",
      "statement": "Orders публикует order.created при успешном создании заказа",
      "evidence": [{"kind": "code", "ref": "internal/orders/service.go:87"}],
      "confidence": "high",
      "status": "candidate",
      "auto_approved": true,
      "question": null
    }]
  }, {
    "batch": "data-ownership",
    "title": "Владение данными",
    "status": "extracting",
    "note": "Агент читает миграции — 41 таблица в 5 схемах"
  }]
}
```

**Числа в `note` не пиши.** Сколько фактов, сколько авто-подтверждено, сколько ждёт решения и
сколько с вопросом — шелл считает сам из `facts[]` и печатает над списком; `note` — про смысл
порции. Агентская арифметика в тексте расходилась с реальностью и подрывала доверие ко всему
экрану.

**Перепуш порции безопасен для ввода человека.** Если он в этот момент что-то решал и не отправил,
шелл не перерисовывает экран молча: сверху появляется плашка «агент прислал обновлённую версию» с
кнопкой — до нажатия его решения остаются на месте.

`status` порции: `extracting` (агент ещё извлекает — в сайдбаре видно, что срез в работе),
`ready` (ждёт человека), `applied` (решения человека применены агентом). Публикуй батч со
`status: "extracting"` **сразу после выбора срезов** — человек видит план и прогресс, а не пустой
экран. Отправленное человеком помечается автоматически (по `decisions.jsonl`), выставлять
`status` для этого не нужно.

Старый формат (один батч в корне: `batch`/`title`/`facts`) шелл продолжает понимать.

Мини-ядро факта: `id`, `statement`, `evidence[]`, `confidence`, `status` (+ `auto_approved`,
`question`, `human_notes` понимает шелл). **Любые другие поля разрешены** — UI показывает их
в развороте карточки как есть.

**Транспорт плоский, память — типизированная.** В `review.json` факт любого среза едет одной
карточкой; в xmemory он лежит в объекте своего среза, схему которого агент спроектировал под
проект ([memory-protocol.md](memory-protocol.md)). Предметные поля просто уезжают в карточку рядом
с ядром — шелл покажет их в развороте, и человек отревьюит их наравне со `statement`. Менять шелл
под типизацию не нужно.

UI-правило авто-подтверждения: `auto_approved: true` — свёрнутая секция «Авто-подтверждено ✓»
с кнопкой «отозвать» на каждом факте; остальные — карточки с Принять/Отклонить/Комментировать;
`question`/`confidence: low` — выделенная секция «Нужен ваш ответ» сверху.

Решение — по одной порции за раз (их прилетит столько, сколько батчей):
```json
{"stage":"review","type":"review","data":{
  "batch": "event-graph",
  "fingerprint": "1q2w3e",
  "decisions": {"fact:eg-0002": {"action": "approve", "comment": "и уточни консюмера"}},
  "global_comment": ""
}}
```
`action`: `approve` | `reject` | `unapprove` (отзыв авто-подтверждения → назад в candidate) |
`skip`. `fingerprint` — служебное поле шелла (отпечаток версии порции, по нему UI помнит, что уже
отправлено); агент его игнорирует. Экспорт-кнопка «скопировать ревью JSON» остаётся как фоллбек,
если агент умер.

### `site/site.json` — сайт-эксплорер (стадия `explore`)

Конструктор: страницы из блоков. Набор блоков — тулкит, не клетка: не хватает — блок `html`
с токенами из [design.md](design.md).

```json
{
  "project": "services-platform",
  "generated_at": "2026-08-27T12:00:00Z",
  "pages": [{
    "id": "overview", "title": "Обзор", "icon": "home",
    "blocks": [
      {"type": "markdown", "md": "## Что это за система\n..."},
      {"type": "stats", "items": [{"label": "Фактов", "value": 37}, {"label": "Активных", "value": 31}]},
      {"type": "mermaid", "title": "Модули и зависимости", "code": "flowchart LR\n A --> B"},
      {"type": "facts", "title": "Инварианты", "filter": {"type": "invariants", "status": ["active"]}, "group_by": "status"},
      {"type": "table", "title": "Флаги", "columns": ["Флаг", "Что переключает", "Evidence"], "rows": [["new_pricing", "v2-алгоритм", "pricing.go:42"]]},
      {"type": "html", "html": "<div class=\"card\">…</div>"}
    ]
  }]
}
```

Блок `facts` тянет из `facts.json` (фильтр по любым полям: точное значение или массив значений).
Шелл добавляет поверх: сайдбар-навигацию по страницам, глобальный поиск по фактам,
фильтр статусов, переключатель темы. Evidence `файл:строка` — моноширинно, клик копирует путь.

## Ответственность

- **Шелл** (в скилле, один раз): рендер стадий и блоков, сайдбар и маршрут, темы, поиск,
  отправка решений, память о том, что уже отправлено.
- **Агент** (каждый проект): содержимое — какие срезы предлагать, чем их проиллюстрировать, какие
  страницы и блоки собрать, какие диаграммы нарисовать, что авто-подтвердить. Агент решает «что»,
  шелл — «как выглядит».
