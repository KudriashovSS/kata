# kata — системный дизайн как память агента

Хакатон агентской памяти. Гипотеза, которую проверяем:

> **Память технических фактов о системном дизайне проекта (в xmemory) улучшает работу
> кодового агента** — меньше токенов и переделок, меньше архитектурных ошибок.

Инвертируем задачу системного анализа: не проектируем схему знаний заранее и не предсказываем
будущее — агент **реверс-инжинирит технические факты из уже существующего кода**, человек только
выбирает нужные срезы и ревьюит сомнительное. Дальше эта память живёт рядом с проектом,
актуализируется при каждой задаче и (гипотеза) делает будущие реализации качественнее и дешевле.

Наша работа = **хороший скилл + честные эвалы**. Всё остальное делает фронтир-модель на вайбе.

## Happy path

1. Пользователь вызывает скилл `/tech-facts`.
2. Агент разведывает репозиторий и поднимает **локальный UI** (`localhost:4747`): лендинг-picker
   со срезами системного дизайна, которые реально есть в этом проекте.
3. Пользователь отмечает нужные срезы прямо на странице — решение уезжает агенту само
   (блокирующий `await`, без копипасты JSON в чат).
4. Агент извлекает срезы параллельно, пишет факты в **xmemory** (схему проектирует сам под
   выбранные срезы), уверенное подтверждает сам, сомнительное отдаёт человеку на ревью.
5. Дальше агенту дают поток задач: перед задачей он **читает** релевантные факты, после —
   **дополняет и актуализирует** память (через хуки).
6. Эвал сравнивает прогоны: **без памяти** vs **с памятью**.
7. *(этап 2, только если останется время)* Между задачами — фаза **самоулучшения**: отдельная
   сессия дедуплицирует факты, правит схему, помечает устаревшее; третий прогон сравнивается
   с первыми двумя.

## Порядок работ: сначала off vs on, самоулучшение — потом

> **Этап 1 (делаем сейчас, до дедлайна): только два режима — `memory-off` и `memory-on`.**
> Основная гипотеза проверяется именно этой парой. Пока нет зелёного сравнения off/on на реальном
> датасете, **самоулучшение памяти не делаем** — ни в раннере, ни в каркасе, ни в скилле.
>
> **Этап 2 (если останется время): `memory-on+evolve`.** Берёмся за него только после того, как
> этап 1 отработан end-to-end и метрики сведены. Всё, что помечено «этап 2» в
> [`dataset/`](dataset/) и [`harness/`](harness/), — задел на будущее, не задача на эти дни.
>
> Почему так: самоулучшение добавляет вторую переменную в эксперимент. Если запустить его раньше,
> мы не сможем сказать, что именно дало эффект — память или её эволюция. И это самая дорогая часть
> по времени и по usage xmemory, которого у нас и так впритык.

## Сверка с ТЗ спринта

Статусы честные: **готово** — работает и прогонялось; **описано** — зафиксировано в протоколе
скилла, исполняет агент, на потоке задач не проверено; **план** — кода ещё нет; **пробел** — не
закрыто, нужно решение.

### Минимальные требования

| Требование ТЗ | Что у нас | Статус |
| --- | --- | --- |
| Обрабатывать поток задач из выбранного источника | Задачи из датасета (реальные фичи целевого репо), каждая — новая сессия | план — [`dataset/`](dataset/) |
| Цикл «выполнил → **оценил** → извлёк урок» | U3: после задачи реальность сверяется с памятью, расхождения → `stale` + новые `candidate`, грабли → факт `gotcha` | описано ([SKILL.md](skills/tech-facts/SKILL.md)), **шаг «оценил» — пробел**, см. ниже |
| Уроки меняют поведение | U1: перед задачей 5–20 релевантных `active`-фактов + `human_notes` уезжают в контекст, факт чтения журналируется | описано, измеряется эвалом |
| Память переживает рестарты | xmemory как первичное хранилище (fallback — файлы вне репозитория), сессия на задачу | готово (полевой тест) |
| Показать дельту «чистая память vs обученная» | Прогоны `memory-off` / `memory-on` + кривая «память после 25/50/100% задач» | план — [`harness/`](harness/), [evals](evals/README.md) |

### Дополнительные блоки

| Блок ТЗ | Что у нас | Статус |
| --- | --- | --- |
| Забывание и устаревание | Жизненный цикл `candidate → active → stale`, ничего не удаляется — только смена статуса с `status_reason`; читаются только `active` | описано |
| Разрешение противоречий | Правило «код прав»: проигравший факт → `stale` + `superseded_by`, неразрешимое кодом — эскалация человеку | описано |
| Human-in-the-loop | Picker срезов, ревью карточек ✓/✗/💬, авто-подтверждение с возможностью отзыва, `human_notes` едут в контекст будущих агентов | готово (сильная часть) |
| Observability | Журналы `memory_read` / `memory_write` / `memory_review` с явными id фактов; attribution «факт → пройденная проверка» в эвалах | описано + план |
| Эвалы для изменений поведения | — | **пробел**: наши эвалы меряют пользу памяти целиком, а не «полезен ли конкретный урок, прежде чем менять поведение» |

### Что честно не закрыто

1. **Шаг «оценил результат».** Сейчас после задачи агент сверяет память с кодом, но не оценивает
   собственную работу — сработало или нет. Дешёвый источник сигнала уже есть: сборка и тесты
   репозитория в прогоне. Их результат стоит заводить в U3 как вход для `gotcha`-фактов.
2. **Источник уроков.** ТЗ просит агента, который учится **на своих результатах**; у нас основной
   источник фактов — реверс-инжиниринг кода. Уроками из собственной работы у нас пока являются
   только `gotcha`-факты из U3 — это та часть, которую стоит усиливать.
3. **Фокус ТЗ — «механизмы памяти и самоулучшения».** Самоулучшение у нас этап 2 (см. «Порядок
   работ»). Порядок оставляем, но помним: сдача **8 сентября**, а не 30 августа — после зелёного
   off/on время на этап 2 есть, и по критерию «количество и качество дополнительных идей» он
   заметно добавляет.
4. **Эвал «полезен ли урок».** Нужно решить, делаем ли мини-проверку урока перед его активацией,
   или честно говорим, что этот блок не брали.

### Номинация xmemory

| Критерий | Как ложится |
| --- | --- |
| Значимый цикл write → read и durability | Факты пишутся на извлечении и после каждой задачи, читаются перед следующей — между сессиями, агентами и процессами; вручную контекст не переносится |
| Схема под задачу | Агент проектирует схему под выбранные срезы и эволюционирует её; в графе есть связи факт ↔ ревью ↔ задача, а не мешок текста |
| xmemory как часть продукта | Без памяти основной сценарий не работает: весь `memory-on` держится на чтении фактов из xmemory |
| Наглядность результата | Сайт-эксплорер над памятью + журналы: видно, что записано, что прочитано в задачу и что изменилось |

## Глоссарий

- **тип факта** — описание элемента системного дизайна (внешние интеграции, зависимости модулей).
- **факт** — собираемая единица: «сервис А ходит в сервис Б», «модуль С зависит от модуля Д».
- **срез** — набор типов фактов, который человек выбирает в picker'е.
