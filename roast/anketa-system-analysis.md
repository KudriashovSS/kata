# База знаний о проекте

Ценность проекта в том что разработка переходить на следующий уровень абстракции к системному анализу. Сам код уже неявляется важным аспектом в разработке. Наличие непротиворечивого описания разрабатываемой системы удобного для манипуляции человеком и агентами выходит на первый план.

На вход формальное описание требуемого проекта, ограничения, формат результата.  На выходе структурированная и связанная документация: требования, ADR, use cases, design docs, specs (HTTP, event operations), БД связанных сущностей полученных в результате системного анализа.

* разработка с ограничениями (чтобы итерации были короткими): задается количество операций, use cases.
* ревью человеком и агентами.
* хранение в xmemory. свои разработки вокруг того: как выглядит схема структурированных требований к Системе, получение фактов для хранения (может ли это xmemory?).

## Проверки (evaluations):

1. генерация документации без памяти и с памятью. проверка конечного результата (количество полученных документов, качество, полнота).
2. внесение изменений в проект, с памятью и без (качество, полнота изменений).

скорее цель для хакатона это 2 вариант. показать как работает память проекта при его разрастании, как это помогает команде. Плюс обвязка по вычленению фактов при разработке проекта.

## Требования к проекту

### Обрабатывать поток задач из выбранного источника

* в рамках проекта просто требования от человека переданные агенту через чат

### Цикл «выполнил → оценил → извлёк урок»

* разработка артефактов,
* оценка агентами,
* оценка людьми,
* обратная связь,
* анализ рута,
* вычленение факта на изменение,
* помещение в очередь на проверку
  * проверка что такой факт уже проверяется, тогда ожидание и перегенерация
  * если факта нет, то запуск перегенерации с новым фактом (факт должен быть изолирован от остальной системы)
  * оценка что проблемы больше нет и не появилось новых, если нет, то повторение или блокировка по какому либо признаку.
  * внесение факта в общедоступный БЗ

### Память переживает рестарты

* используем xmemory для стуктурированного храненеия данных о системном анализе.
  * плюс это использование инструмена уже заточенного под структурированное хранение фактов о реальном мире и выполнение дополнительного условия хакатона.

### Обучиться на своих данных до финала, показать дельту чистая/обученная

* Возможно есть проблема с разделением БД системного анализа (процесса) и БД готовых фактов проекта. По идее это разные знания.
* Берем начальные требования и просим сгенерить агента с памятью о системном анализе и без. Сверяем проработку требований.
* Берем готовый провект и вносим различные изменения: расширения требований, изменение требований, конфликтующие требования. Используем агента без памяти и с памятью структурированной о проекте + память о системном анализе.

### Забывание и устаревание

* естественный процесс при работе с требованиями в проекте
* отметка фактов в памяти как устаревших на определенный момент, но когда-то применявшихся.

### Разрешение противоречий

* на основе свежести факта
* по количеству ссылок на факт подтверждающих его актуальность
* по актуальности причины внесения фактов. сравнение актуальности разных причин и их конфликта.

### Human-in-the-loop

* возможность подтверждения внесения факта человеком без евала (подумать как это сделать)
* внесение обязательной отметки всех проверренных фактов человеком. асинхронный просмотр.

### Observability

* тут как и у всех проектов, по идее в любом случае надо иначе сложно понять эффективность работы агента с памятью и без.

### Эвалы для изменений поведения 

* определенные срезы документации проекта в ветке + синхронизированная память в xmemory (как делать слепки? форки?)

### Можно доставать причину факта

* важная часть проекта системного анализа. иначе факты превращаются в домыслы без возможности решать конфликты.
