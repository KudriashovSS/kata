# tech-facts: база технических фактов о проекте

Ты строишь и поддерживаешь **реляционную память о технической реальности проекта**: только факты,
извлечённые из существующего кода, каждый с evidence. У памяти два потребителя: **человек**
понимает систему через локальный UI-сайт, **агенты** читают факты из xmemory перед задачей,
чтобы решить её правильно с первого раза.

Справочники: [fact-catalog.md](fact-catalog.md) — срезы и как их извлекать,
[memory-protocol.md](memory-protocol.md) — модель памяти и авто-подтверждение,
[ui-protocol.md](ui-protocol.md) — сервер, стадии UI и форматы JSON,
[design.md](design.md) — дизайн-система (нужна только если делаешь custom-блоки).

## Железные правила (в любом состоянии)

1. **Факт без evidence не существует.** Минимум один `файл:строка`, коммит или конфиг.
2. **Не выдумывай.** Провенанс честный: `declared`/`observed`/`inferred`; сомнение → `confidence:
   low` + `question` человеку, а не истина.
3. **Код прав, память — нет.** Расхождение → факт `stale` + новый `candidate`, вслух.
4. **Ничего не удаляется** — только `candidate → active → stale` со `status_reason`.
5. **Не таскай человека по мелочам.** Уверенное (high + declared/observed + evidence)
   подтверждай сам с пометкой `auto_approved`; человеку — только сомнительное. Его комментарии —
   в `human_notes`, они едут в контекст будущих агентов.
6. **Источник истины — xmemory**, и факт попадает туда на извлечении, а не после ревью. Файлы в
   workdir — витрина; правки фактов живут только в памяти. Пишешь `structured_mutations`-батчем,
   никогда прозой ([почему](memory-protocol.md)).
7. **Обращения к памяти журналируй** (memory_read / memory_write / memory_review, только явные id).

## Стейт-машина

Определи состояние ПЕРВЫМ действием: у проекта есть xmemory-инстанс или локальная память
`~/.tech-facts/<slug-проекта>/` → **U1 (использование)**; памяти нет и просят построить →
**B1 (строительство)**.

Обозначения: `WORKDIR=${TMPDIR:-/tmp}/tech-facts/<slug-проекта>`, `SRV=node <skill>/scripts/server.mjs`.
Сервер один на проект, порт один (default 4747), стадии сменяются на одном URL.

### Строительство

**B1 · Разведка и выбор хранилища** — 10–15 минут, без записи в память.
Языки, модули, брокер/in-process события, планировщики и джобы, готовые контракты
(openapi/proto/graphql), миграции, IaC, Options/флаги, ADR. Для каждого среза каталога пересчитай
под этот репозиторий звёзды и стоимость; срезы, которых в проекте нет, не предлагай (но проверяй
суть, а не буквальные маркеры; условные срезы — только при их артефактах).

**Здесь же реши, куда ляжет память** — от этого зависит формат всего извлечения, узнавать об этом
после ревью поздно. Проверь xmemory: `xmemcli auth status` (нет бинаря — `uv tool install xmemcli`;
не авторизован — `xmemcli auth login`: он печатает ссылку и ждёт человека, не жди сам и не заворачивай
в пайп; креды `.xmemrc.json` ищутся от текущей директории вверх, [детали](memory-protocol.md)).
Недоступен — **спроси человека**, а не решай за него: дать доступ (где креды / какой инстанс) или
строим локально «просто посмотреть» — тогда память ляжет в `~/.tech-facts/<slug>/` вне репозитория,
не шарится с командой и живёт на одной машине. Выбранный режим положи в блок `memory` в
`picker.json` — UI будет держать предупреждение на экране, пока память локальная. → B2.

**B2 · Выбор срезов.** Собери `WORKDIR/picker.json` ([формат](ui-protocol.md)) из находок
разведки. Первый экран человек читает 15 секунд, а не изучает:

- одна строка сути на карточку (`summary`), всё длинное — в `found`/`value`/`auto_note`, они под
  «подробнее»; `intro` — 2 предложения, не абзац;
- `recommended: true` — **не больше трёх** срезов: минимальный набор, который даёт максимум связей
  (шелл отметит галочкой только их). Остальные предлагай невыбранными — их включают одним кликом;
- к каждому срезу **нарисуй иллюстрацию сам** — инлайновый SVG в поле `art`. Что рисовать, тебя
  никто не ограничивает: это твоя картинка про суть **этого** среза в **этом** репозитории, а не
  иконка из набора. Технические рамки (viewBox, токены цвета, никаких внешних ссылок) — в
  [ui-protocol.md](ui-protocol.md).

```bash
$SRV serve --workdir $WORKDIR --open   # в фоне, один раз за сессию
$SRV push picker --workdir $WORKDIR
$SRV await --workdir $WORKDIR --timeout 540   # exit 3 = таймаут → просто перезапусти
```
Дай человеку ссылку. Решение придёт JSON-ом в stdout `await`. Пользователь управляет сложностью:
один срез — валидный выбор. → B3.

**B3 · Извлечение — параллельное.** Сразу после выбора опубликуй все выбранные срезы порциями со
`status: "extracting"` — человек видит план и прогресс, а не пустой экран. Дальше извлекай срезы
**независимо друг от друга** (субагентами, если инструмент позволяет) и публикуй каждую порцию,
как только она готова: допиши батч в `review.json` со `status: "ready"` и `push review`. Не жди
ревью предыдущего среза — человек разбирает готовое, пока ты достаёшь остальное.

Внутри среза — по каталогу: сначала сущности, потом связи; id с префиксом среза; фильтруй шум;
большой репозиторий — по одному bounded-контексту. Каждый факт: мини-ядро + провенанс. Примени
авто-подтверждение по [memory-protocol.md](memory-protocol.md). Одна порция — один срез
(>20 карточек человек теряет факты — проверено). Числа в `note` не пиши: сколько фактов,
сколько авто-подтверждено и сколько ждёт решения, шелл считает сам — в `note` оставляй смысл.
`push` проверит мини-ядро (id, statement, evidence) и упадёт со списком виноватых id: это твои же
железные правила, чинить их, а не обходить.

**Факт рождается в памяти, а не в файле.** Готовую порцию сначала уложи в xmemory одним
`structured_mutations`-батчем — сущности, факты, связи, статусы `candidate`/`active` как решило
авто-подтверждение ([как](memory-protocol.md)) — и только потом `push review`. Порядок именно такой:
`review.json` — копия для человека, источник истины уже в памяти. Так извлечение переживает падение
сессии, а ревью становится сменой статуса, а не первичной записью. Словарь сущностей заводи здесь же,
до фактов: `subject`/`object` факта — это `entity_id`, а не свободная строка, иначе на переносе
выяснится, что половина «сущностей» — описания, и сводить их придётся руками. → B4 идёт параллельно,
не после.

**B4 · Ревью — по мере готовности.** Крути цикл, пока извлечение продолжается:
```bash
$SRV await --workdir $WORKDIR --timeout 540   # без --stage: решения приходят вперемешку
```
Разбирай пришедшее по `type`:

- `review` — примени решения к своей порции: approve → `active`; reject → `stale/rejected`;
  unapprove → отзыв авто-подтверждения в `candidate`; comment → `human_notes` (правит формулировку
  → перезапиши факт: старый stale, новый active, source human); без решения → остаётся
  `candidate`, молча не активируй. Применяй мутацией `update` по `fact_id` — статус,
  `status_reason`, `human_notes`; факт уже в памяти с B3, новых записей здесь не создаётся. Затем
  то же самое в витрине: батч `status: "applied"`, `push review`, запиши memory_review;
- `picker_amend` — человек передумал: `added` доизвлеки и добавь новой порцией (сначала
  `extracting`, потом `ready`), `removed` — останови извлечение и не сохраняй; уже сохранённое по
  этому срезу → `stale/rejected` со `status_reason`, скажи вслух.

Все порции `applied` → B5.

**B5 · Верификация и журналы.** Факты уже в памяти с B3 — здесь закрываешь долг: journal-записи
(`memory_review`, `memory_write`) явными id и **обязательная верификация**. Сверяй множества ключей
диффом с витриной в `--read-mode raw`, а не числа из прозаического ответа: пересчёт по срезам сходится
и при потерянных сущностях и придуманных связях ([как проверять](memory-protocol.md)). Поверх диффов —
обход графа и агентская выборка. Расхождение чини сейчас, не откладывая на «потом посмотрим». → B6.

**B6 · Сайт.** Собери витрину под проект — какие страницы и блоки нужны ИМЕННО этой системе
(конструктор блоков в [ui-protocol.md](ui-protocol.md); не хватает блока — `html` с токенами из
design.md). Выгрузи из памяти `site/facts.json`, собери `site/site.json`, затем `push explore`.
Сайт можно перегенерировать в любой момент («покажи event graph») — это витрина над xmemory.
Опционально: клиент поддерживает Artifacts → `$SRV export --fragment --out page.html`
(без `<!doctype>/<html>/<body>` — ровно то, что принимает Artifact-тул) и опубликуй read-only
версию для шаринга. Без `--fragment` получится самодостаточный файл — его можно просто отдать
коллеге. → B7.

**B7 · Отчёт.** memory_write в журнал; человеку: сколько фактов (авто/вручную подтверждённых),
какие срезы, открытые вопросы, ссылка на сайт.

### Использование и актуализация (цикл, ради которого база существует)

**U1 · Перед задачей.** Определи затронутые сущности → достань 5–20 релевантных `active`-фактов
обходом связей (+`human_notes`) → блок «Известные факты о проекте» в рабочий контекст →
memory_read. → задача.

**U2 · Во время.** Факт разошёлся с кодом → правило «код прав»: `stale` + новый `candidate`,
скажи человеку. Не молчи.

**U3 · После задачи.** Реальность изменилась (новое событие/зависимость/endpoint/инвариант) →
новые `candidate`-факты (уверенные — auto_approve), устаревшие → `stale` c `superseded_by`.
Наступил на грабли → факт `gotcha` (только как гипотеза). Дифф памяти человеку: ≤10 строк — в чат;
больше — мини-ревью через UI (`push review` только с изменёнными фактами). memory_write.
Сайт запущен → перегенерируй затронутые страницы.

**E · Эволюция памяти** — отдельной сессией между задачами или по cron:
дедупликация фактов, снятие протухших, схлопывание шума, предложение новых типов фактов под
накопившиеся `gotchas`/вопросы (+ расширение схемы xmemory), перегенерация сайта. Все изменения —
через candidate/review-цикл, крупные — с ревью человека через UI. Итог — memory_write с явными id.
