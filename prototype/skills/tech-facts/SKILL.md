# tech-facts: база технических фактов о проекте

Ты строишь и поддерживаешь **реляционную память о технической реальности проекта**. Не документацию
и не предсказание будущего — только факты, извлечённые из существующего кода, каждый с evidence.

Два режима. Определи режим ПЕРВЫМ действием:

- В репозитории есть `.tech-facts/` или настроенный xmemory-инстанс проекта → режим
  **[Использование и актуализация](#режим-2-использование-и-актуализация)**.
- Памяти нет, пользователь просит построить базу → режим **[Строительство](#режим-1-строительство)**.

Сопутствующие файлы: [fact-catalog.md](fact-catalog.md) — типы фактов и как их извлекать,
[memory-protocol.md](memory-protocol.md) — модель памяти и адаптеры,
[references/picker.html](references/picker.html) — референс UI выбора срезов.

## Железные правила (оба режима)

1. **Факт без evidence не существует.** Каждый факт ссылается минимум на один `файл:строка`,
   коммит или конфиг. Не можешь показать пальцем — не записывай.
2. **Не выдумывай.** Извлечение — это чтение кода, не додумывание архитектуры. Если что-то
   неочевидно, записывай с `confidence: low` и вопросом к человеку, а не как истину.
3. **Код прав, память — нет.** Обнаружил расхождение факта с кодом → факт помечается `stale`
   с причиной, создаётся новый `candidate`. Никогда не «подгоняй» прочтение кода под память.
4. **Ничего не удаляется.** Только смена статуса: `candidate → active → stale`. История — часть
   ценности памяти.
5. **Человек — гейт.** `active` факт делает только подтверждение человека. Ты предлагаешь,
   человек решает.
6. **Каждое обращение к памяти журналируется.** Прочитал факты перед задачей — запиши MemoryRead.
   Изменил память — запиши MemoryWrite. Без этого невозможно показать, что память работает.

## Режим 1: Строительство

### Фаза 1 — Разведка (10–15 минут, без записи в память)

Быстро пойми, из чего состоит проект: языки, структура модулей/сервисов, есть ли брокер сообщений,
HTTP/gRPC-слои, миграции БД, конфиги, фичефлаги. Цель — определить, какие типы фактов из
[fact-catalog.md](fact-catalog.md) **реально присутствуют** в этом репозитории и примерно оценить
стоимость извлечения каждого (S/M/L по критериям каталога).

Не предлагай пользователю срезы, которых в проекте нет (event graph в монолите без событий — мусор).

### Фаза 2 — Выбор срезов пользователем

Подними локальный picker: сгенерируй одностраничный UI по образцу
[references/picker.html](references/picker.html), заполнив карточки **только релевантными** типами
фактов с найденными в разведке примерами («нашёл 14 событий в `internal/events/`») и оценкой
стоимости. Запусти локальный статический сервер и дай пользователю ссылку.

Пользователь отмечает нужные срезы и жмёт «Собрать» — забери итоговый JSON-конфиг выбора.

Fallback без браузера: задай тот же выбор списком прямо в чате. Смысл фазы не в красоте, а в том,
что **пользователь управляет сложностью**: один срез — тоже валидный выбор.

### Фаза 3 — Извлечение

Для каждого выбранного типа фактов следуй экстракционным подсказкам его раздела в
[fact-catalog.md](fact-catalog.md). Общий порядок:

1. Сначала собери сущности (модули, события, endpoints, таблицы…), потом связи между ними.
2. Каждый факт формулируй одним утверждением в формате из [memory-protocol.md](memory-protocol.md),
   со статусом `candidate`, evidence и confidence.
3. Большой репозиторий — иди по одному bounded-контексту за раз, показывай промежуточные
   результаты, не пытайся съесть всё молча.

### Фаза 4 — Ревью на диаграммах

Покажи извлечённое **человекопонятными диаграммами** (mermaid), по одной на аспект. Правила
«как не UML»:

- ≤ 15 узлов на диаграмму; больше — режь по контекстам или схлопывай в группы;
- бизнес-имена узлов, не имена классов; глагол на каждой стрелке (`produces`, `owns`, `calls`);
- никакой техномишуры (стереотипы, кратности, лямбды) — диаграмма для человека, детали в фактах;
- рядом с диаграммой — список фактов с low confidence как явные вопросы человеку.

Человек правит и подтверждает. Подтверждённые факты переводи в `active`, исправленные — перезаписывай
(старый `stale`, новый `active` с source `human`), отклонённые — `stale` с причиной `rejected`.

### Фаза 5 — Сохранение

По [memory-protocol.md](memory-protocol.md): предложи схему хранения под выбранные срезы, покажи её
человеку, после подтверждения сохрани факты. xmemory-инстанс доступен → xmemory-адаптер (схему
создаёшь сам под выбранные типы фактов, она сможет дорасти при добавлении срезов). Недоступен →
файловый адаптер `.tech-facts/`. Заверши сессию MemoryWrite-записью и коротким отчётом: сколько
фактов, каких типов, сколько вопросов осталось открытыми.

## Режим 2: Использование и актуализация

Это цикл, ради которого база существует. Работая над ЛЮБОЙ задачей в проекте с памятью:

### Перед задачей — читай

1. Определи, каких модулей/сущностей касается задача.
2. Достань релевантные `active`-факты (только active!) — по связям затронутых сущностей, а не всю
   базу. Обычно 5–20 фактов; не раздувай контекст.
3. Вставь их в свой рабочий контекст отдельным блоком «Известные факты о проекте» и запиши
   MemoryRead: какие факты, для какой задачи.

### Во время задачи — сверяй

Факт противоречит тому, что ты видишь в коде → правило «код прав»: пометь факт `stale`, создай
`candidate` с новым прочтением, скажи человеку. Не молчи и не игнорируй расхождение.

### После задачи — актуализируй

1. Твоя реализация изменила реальность (новое событие, новая зависимость, новый endpoint, снятый
   инвариант)? Создай соответствующие `candidate`-факты, устаревшие пометь `stale` с
   `superseded_by`.
2. Наступил на грабли, которых не было в памяти? Это лучший урожай — оформи как факт типа
   `gotcha` с evidence.
3. Покажи человеку дифф памяти (2–10 строк, не простыня) на подтверждение. Запиши MemoryWrite.

Так замыкается цикл: выполнил задачу → сверил память с реальностью → извлёк урок → следующий агент
начинает умнее.
