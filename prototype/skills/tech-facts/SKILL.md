# tech-facts: база технических фактов о проекте

Ты строишь и поддерживаешь **реляционную память о технической реальности проекта**. Не документацию
и не предсказание будущего — только факты, извлечённые из существующего кода, каждый с evidence.

У памяти два потребителя, и скилл обслуживает обоих:

- **Человек** смотрит на факты через **HTML-вьюверы** — по странице на срез, с диаграммами,
  evidence и комментариями. Цель: быстро понять, что за система перед ним.
- **Агенты** читают факты из **xmemory** перед задачей. Цель: решить задачу правильно с первого
  раза — не нарушить инвариант, не забыть консюмера, не наступить на известные грабли.

Два режима. Определи режим ПЕРВЫМ действием:

- В проекте есть xmemory-инстанс или `.tech-facts/` → режим
  **[Использование и актуализация](#режим-2-использование-и-актуализация)**.
- Памяти нет, пользователь просит построить базу → режим **[Строительство](#режим-1-строительство)**.

Сопутствующие файлы: [fact-catalog.md](fact-catalog.md) — типы фактов и как их извлекать,
[memory-protocol.md](memory-protocol.md) — модель памяти и адаптеры,
[references/picker.html](references/picker.html) — референс UI выбора срезов,
[references/viewer.html](references/viewer.html) — референс UI ревью и чтения фактов.

## Железные правила (оба режима)

1. **Факт без evidence не существует.** Каждый факт ссылается минимум на один `файл:строка`,
   коммит или конфиг. Не можешь показать пальцем — не записывай.
2. **Не выдумывай.** Извлечение — это чтение кода, не додумывание архитектуры. Если что-то
   неочевидно, записывай с `confidence: low` и вопросом к человеку, а не как истину.
3. **Код прав, память — нет.** Обнаружил расхождение факта с кодом → факт помечается `stale`
   с причиной, создаётся новый `candidate`. Никогда не «подгоняй» прочтение кода под память.
4. **Ничего не удаляется.** Только смена статуса: `candidate → active → stale`. История — часть
   ценности памяти.
5. **Человек — гейт.** `active` факт делает только подтверждение человека (обычно через ревью
   во вьювере). Ты предлагаешь, человек решает. Комментарии человека — часть факта
   (`human_notes`), они едут в контекст будущих агентов вместе с фактом.
6. **Обращения к памяти журналируются.** В режиме строительства журнал начинается с MemoryWrite —
   MemoryRead там не возникает, это нормально. В режиме использования обязательны оба: прочитал
   факты перед задачей → MemoryRead; изменил память → MemoryWrite.

## Режим 1: Строительство

### Фаза 1 — Разведка (10–15 минут, без записи в память)

Быстро пойми, из чего состоит проект: языки, структура модулей/сервисов, есть ли брокер сообщений
или in-process события, HTTP/gRPC-слои и **готовые контракты** (openapi/proto/graphql-спеки),
миграции БД, конфиги/Options-классы, ADR и docs-каталоги. Цель — определить, какие типы фактов из
[fact-catalog.md](fact-catalog.md) **реально присутствуют** в этом репозитории.

По итогам разведки **обязательно пересчитай стоимость S/M/L каждого среза** для этого конкретного
репозитория (каталожная оценка — только стартовая: найденные спеки удешевляют api-contracts,
отсутствие брокера меняет способ извлечения event-graph и т.д.). В picker идут пересчитанные оценки.

Не предлагай пользователю срезы, которых в проекте нет. Но помни: срез может присутствовать в
другой форме, чем ожидает каталог (фичефлагов нет, а Options-классы переключают поведение) —
проверяй суть среза, а не буквальные маркеры.

### Фаза 2 — Выбор срезов пользователем

Основной путь — **гибрид**: сгенерируй picker-страницу по образцу
[references/picker.html](references/picker.html), заполнив карточки только релевантными типами
фактов с находками разведки («нашёл 14 событий в `internal/events/`») и пересчитанной стоимостью;
запусти локальный статический сервер и дай пользователю ссылку **для просмотра**. Выбор же прими
структурированным вопросом в чате, куда пользователь вставляет JSON-конфиг с picker-а (или просто
называет срезы) — не полагайся на автоматический возврат данных из браузера.

Смысл фазы: **пользователь управляет сложностью**. Один срез — тоже валидный выбор.

### Фаза 3 — Извлечение

Для каждого выбранного типа фактов следуй экстракционным подсказкам его раздела в
[fact-catalog.md](fact-catalog.md). Общий порядок:

1. Сначала собери сущности (модули, события, endpoints, таблицы…), потом связи между ними.
2. Каждый факт формулируй одним утверждением в формате из [memory-protocol.md](memory-protocol.md),
   со статусом `candidate`, evidence и confidence. Id фактов — с префиксом среза (`fact:eg-0001`),
   чтобы параллельное извлечение срезов не коллидировало.
3. Фильтруй шум: тривиальные следствия структуры (leaf-ность модуля, «Api зависит от всех» в
   стандартном шаблоне) не записывай или схлопывай в один факт о шаблоне с отклонениями.
4. Большой репозиторий — иди по одному bounded-контексту за раз, показывай промежуточные
   результаты, не пытайся съесть всё молча.

### Фаза 4 — Ревью во вьювере

Ревью — это **HTML-страница, а не простыня в чате**. Сгенерируй вьювер по образцу
[references/viewer.html](references/viewer.html), подставив реальные данные: срезы в сайдбаре,
mermaid-диаграмма среза сверху, ниже — карточки фактов (statement, evidence, confidence, статус).
Подними локальный сервер и дай ссылку. В клиентах без локального браузера — опубликуй страницу
артефактом/превью.

Правила диаграмм: одна на аспект/срез; резать по событию или домену — только при переполнении
(> ~15 узлов). Бизнес-имена узлов, глагол на каждой стрелке (`produces`, `owns`, `calls`), никакой
техномишуры. Факты с low confidence — явные вопросы человеку, они должны бросаться в глаза.

Человек в вьювере принимает (✓), отклоняет (✗) и комментирует (💬) факты, затем возвращает тебе
ревью-JSON (кнопка «Экспортировать ревью» кладёт его в буфер; принять его — структурированным
вопросом в чате, как в фазе 2). Примени решения:

- `approve` → факт `active`;
- `reject` → факт `stale` с `status_reason: rejected`;
- `comment` → сохрани в `human_notes`; если комментарий исправляет формулировку — перезапиши факт
  (старый `stale`, новый `active`, source `human`);
- факты без решения остаются `candidate` — не активируй их молча.

Запиши ревью в журнал (`memory_review`).

### Фаза 5 — Сохранение

Первичное хранилище — **xmemory**: по [memory-protocol.md](memory-protocol.md) предложи схему под
выбранные срезы, покажи человеку, сохрани факты, сущности, human_notes и журналы. Схему создаёшь
сам, она дорастает при добавлении срезов. xmemory недоступен → файловый адаптер `.tech-facts/`
(тот же формат; при появлении xmemory мигрируй).

Вьювер при этом остаётся **режимом чтения для человека**: его можно перегенерировать из памяти в
любой момент («покажи мне event graph») — это витрина над xmemory, а не отдельная база.

Заверши сессию MemoryWrite-записью и коротким отчётом: сколько фактов, каких типов, сколько
вопросов осталось открытыми.

## Режим 2: Использование и актуализация

Это цикл, ради которого база существует. Работая над ЛЮБОЙ задачей в проекте с памятью:

### Перед задачей — читай

1. Определи, каких модулей/сущностей касается задача.
2. Достань релевантные `active`-факты из xmemory обходом связей затронутых сущностей (события,
   которые они продюсят/консюмят; таблицы, которыми владеют; их инварианты и грабли) — только
   active, обычно 5–20 фактов, не вся база.
3. Вставь их в рабочий контекст блоком «Известные факты о проекте» — вместе с `human_notes`:
   заметки человека часто ценнее самого факта. Запиши MemoryRead: какие факты, для какой задачи.

### Во время задачи — сверяй

Факт противоречит тому, что ты видишь в коде → правило «код прав»: пометь факт `stale`, создай
`candidate` с новым прочтением, скажи человеку. Не молчи и не игнорируй расхождение.

### После задачи — актуализируй

1. Твоя реализация изменила реальность (новое событие, новая зависимость, новый endpoint, снятый
   инвариант)? Создай соответствующие `candidate`-факты, устаревшие пометь `stale` с
   `superseded_by`.
2. Наступил на грабли, которых не было в памяти? Это лучший урожай — оформи как факт типа
   `gotcha` с evidence.
3. Покажи человеку дифф памяти на подтверждение: пара строк — прямо в чате, больше — мини-вьювером
   только из изменённых фактов. Запиши MemoryWrite.

Так замыкается цикл: выполнил задачу → сверил память с реальностью → извлёк урок → следующий агент
начинает умнее, а человек в любой момент может открыть вьювер и увидеть систему целиком.
