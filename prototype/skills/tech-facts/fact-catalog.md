# Каталог типов технических фактов

Меню для picker-а и инструкции извлечения. Для каждого типа: что это, когда полезен, как извлекать,
формат факта, как рисовать на ревью, стоимость извлечения (S — часы, M — полдня, L — день+ на
средний репозиторий; уточняется в разведке).

Пользователь выбирает любое подмножество — хоть один срез. Каждый срез самодостаточен, но связи
между срезами (событие → модуль-владелец → таблица) делают память кратно полезнее: предлагай
смежные срезы, если пользователь выбрал один из пары.

---

## 1. `event-graph` — граф событий · **S–M**

**Что:** кто продюсит какие события и кто их консюмит.
**Когда полезен:** событийные и in-process-событийные системы; главный источник ошибок «забыл
уведомить консюмера».
**Как извлекать.** Два подтипа, определи в разведке какой перед тобой:
- *брокерные события*: поиск по publish/emit/produce и subscribe/consume/handler; топики и routing
  keys из конфигов брокера; схемы событий (avro/proto/json-schema) как атрибуты;
- *in-process доменные события*: grep по publish даёт мусор — источник истины в DI-регистрациях
  подписчиков (`AddSingleton<ISubscriber<T>>`, MediatR-хендлеры, event-bus регистрации) и в коде
  диспетчера событий.
Для обоих подтипов **обязательный факт среза — семантика доставки**: sync/async, порядок,
поведение при сбое подписчика (валит ли он бизнес-операцию). Это то, что агент без памяти нарушит.
**Факты:** `Orders produces order.created`, `Billing consumes order.created`,
`сбой подписчика логируется и не валит бизнес-мутацию`.
**Диаграмма:** flowchart «продюсер → событие → консюмеры»; одна на срез/домен, резать по событию —
только при переполнении (>15 узлов):

```
Orders ──produces──► order.created ──► Billing
                                   ──► Notifications
                                   ──► Analytics
```

## 2. `module-graph` — модули и зависимости · **S**

**Что:** крупные модули/сервисы/пакеты и направленные зависимости между ними.
**Когда полезен:** всегда; каркас, к которому цепляются остальные срезы.
**Как извлекать:** структура каталогов + import/reference-анализ; в полирепо — по манифестам
зависимостей. Только крупные блоки, не классы.
**Анти-шум:** не записывай тривиальные следствия структуры («Domain — leaf», «Api зависит от всех»
в стандартном Clean Architecture) отдельными фактами — схлопни в один факт «каркас соответствует
шаблону X, отклонения: …»; отдельного факта заслуживают только отклонения и циклы.
**Факты:** `каркас — Clean Architecture DAG, отклонение: Web напрямую ходит в Infrastructure`.
**Диаграмма:** flowchart зависимостей, циклы подсвечивать отдельным фактом-предупреждением.

## 3. `data-ownership` — владение данными · **M**

**Что:** какие таблицы/коллекции/сущности каким модулем владеются; кто читает или пишет чужое.
**Когда полезен:** любой проект с БД; «кто пишет в эту таблицу» — вечный вопрос.
**Как извлекать:** миграции и модели → владелец; поиск обращений к таблице из чужих модулей —
каждое такое обращение отдельный факт (это будущие грабли).
**Факты:** `orders_table owned by Orders`, `Analytics reads orders_table directly (мимо API)`.
**Диаграмма:** группировка таблиц по владельцам, красные стрелки чужих доступов.

## 4. `api-contracts` — контракты API · **M**

**Что:** HTTP/gRPC endpoints, их назначение и известные потребители.
**Когда полезен:** сервисы с внешними или межсервисными API; страхует от ломающих изменений.
**Как извлекать:** первым шагом ищи **готовые контракты** — openapi/proto/graphql-схемы,
`specs/`, `contracts/` (contract-first репозитории кодогенерят роутинг, grep по атрибутам
`[HttpGet]`/`MapGet` даст ноль). Есть спеки → извлекай из них, стоимость падает до S. Нет —
fallback: роуты/контроллеры/атрибуты. Потребители — по клиентскому коду в соседних модулях и
известным интеграциям. DTO целиком не тащить — только endpoint, метод, назначение, потребители.
**Факты:** `POST /orders создаёт заказ, потребители: mobile-app, partner-gw`.
**Диаграмма:** таблица endpoints по модулям + flowchart потребителей для критичных.

## 5. `external-integrations` — внешние интеграции · **S**

**Что:** внешние системы (платёжки, нотификации, CRM…), направление и точка интеграции в коде.
**Когда полезен:** почти всегда; маленький срез с большой плотностью пользы.
**Как извлекать:** внешние URL в конфигах, SDK в зависимостях, API-ключи в env-примерах.
**Факты:** `Billing вызывает Stripe (charge) из billing/stripe_client.go`.
**Диаграмма:** система в центре, внешние системы по краям, направление стрелок = кто кого вызывает.

## 6. `invariants` — инварианты и ограничения · **L**

**Что:** бизнес-правила, зашитые в код: «заказ нельзя отменить после отгрузки», «сумма не
отрицательная», идемпотентность обработчиков.
**Когда полезен:** зрелые домены; самый ценный и самый дорогой срез — именно его нарушают агенты
без памяти.
**Как извлекать:** валидации, guard-выражения, констрейнты БД, тесты (имена тестов — золото:
`test_cannot_cancel_shipped_order`), комментарии с «нельзя/должен/всегда/никогда».
**Факты:** `Заказ в статусе shipped не может быть отменён (orders/service.py:142, test_...)`.
**Диаграмма:** не рисуется — список по модулям, сгруппированный по сущностям.

## 7. `config-flags` — конфигурация, меняющая поведение · **S**

**Что:** любая конфигурация, переключающая поведение системы: фичефлаги — лишь частный случай.
Сюда же Options-классы, per-env оверрайды (appsettings по окружениям), env-переменные,
установочные интервалы/лимиты.
**Когда полезен:** почти всегда — даже «без фичефлагов» поведение переключают Options и env;
агент без этого знания «чинит» выключенный код или не видит грань dev/staging/prod.
**Как извлекать:** реестр флагов/Options/конфигов + поиск мест ветвления по ним; отдельно —
различия per-env конфигов.
**Ветвление вне репозитория** (флаг уходит в библиотеку): точку ветвления показать нельзя —
записывай факт с `confidence: low` и пометкой «branch point вне репо, в библиотеке X».
**Факты:** `flag new_pricing переключает Pricing на v2-алгоритм (3 точки ветвления)`,
`AuthOptions:Enabled выключен в dev, включён в staging/prod`.
**Диаграмма:** таблица флаг/опция → что переключает → где ветвится.

## 8. `gotchas` — грабли и workarounds · **M**

**Что:** известные неочевидности: флакающие тесты, обязательный порядок вызовов, «не трогай — так
надо», причины ревертов.
**Когда полезен:** всегда; срез с максимальным «вау» на демо и максимальным приростом от
актуализации (пополняется после каждой задачи).
**Как извлекать:** комментарии TODO/HACK/FIXME/WARNING и их локализованные аналоги на языке
команды («нельзя», «не трогать», «важно», «схлопывать нельзя»); предупреждающие doc-комментарии;
**ADR и docs-каталоги** — в дисциплинированных репо грабли живут там, а не в TODO; revert-коммиты
и hotfix-и в `git log`; повторные правки одного места (git churn).
В «чистом» репо срез получается тонким — это нормально и само по себе факт о зрелости проекта;
основной прирост этого среза идёт от актуализации после задач.
**Факты:** `Тесты billing_integration флакают на CI из-за таймаута Stripe-мока (revert abc123)`.
**Диаграмма:** не рисуется — лента по модулям, свежие сверху.

---

## Подсказки по сочетаниям

- Выбран `event-graph` → предложи `module-graph` (S, даёт владельцев событий).
- Выбран `data-ownership` → предложи `invariants` по тем же сущностям.
- Быстрый старт для демо: `module-graph` + `event-graph` + `gotchas` — дёшево, наглядно,
  покрывает и структуру, и динамику, и «опыт».
