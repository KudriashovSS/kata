# Каталог типов технических фактов

Меню для picker-а и инструкции извлечения. Для каждого среза: звёзды автоматизируемости
(★1–5 — насколько честно агент извлекает срез из кода без человека; фактчекнуто по опыту
статических recovery-инструментов и LLM-SAR-исследований), стоимость (S — часы, M — полдня,
L — день+), что реально извлечь и что ломает извлечение. **В разведке обе оценки пересчитываются
под конкретный репозиторий** — найденные спеки удешевляют срез, отсутствие IaC роняет звёзды.

Сквозные правила честности:

- **Провенанс каждого факта**: `declared` (прочитано из декларативного артефакта — спека, миграция,
  конфиг), `observed` (выведено из кода), `inferred` (интерпретация агента). inferred никогда не
  авто-подтверждается.
- **Граница видимости**: в полирепо потребители API, консюмеры событий и деплой уходят за горизонт
  репозитория. Не выдумывай их — записывай явный факт «граница: потребители вне репо не видны».
- Недооценённые источники: имена тестов (инварианты, переходы статусов), CODEOWNERS (границы
  контекстов), contract-тесты (потребители API), диффы `values-{env}` (поведение в проде),
  git-реверты (грабли).

Пользователь выбирает любое подмножество — хоть один срез. Связи между срезами (событие →
модуль-владелец → таблица) делают память кратно полезнее: предлагай смежные срезы.

---

## Основные срезы

## 1. `module-graph` — модули и зависимости · ★★★★★/★★★★☆ · S

**Что:** крупные модули/сервисы/пакеты и направленные зависимости; каркас для остальных срезов.
**Реально извлечь:** import-граф и манифесты зависимостей — ★★★★★ механически (уровень
dependency-cruiser/madge). Границы «компонентов» в смысле C4 — ★★★★☆: папка ≠ компонент,
границы — интерпретация (`inferred`), особенно при дрейфе структуры.
**Как извлекать:** структура каталогов + import/reference-анализ; манифесты (`package.json`,
`go.mod`, `*.csproj`, `pyproject.toml`); DI-регистрации; декларированные архитектурные правила
(ArchUnit, dep-cruiser конфиги) — золото, это `declared`-архитектура; CODEOWNERS.
**Ломает:** динамические импорты, рефлексия и assembly-scanning DI, событийные связи (граф
импортов пуст, а связь есть), god-modules `common/utils`, кодогенерация.
**Анти-шум:** тривиальные следствия шаблона («Api зависит от всех» в Clean Architecture) — один
факт о шаблоне с отклонениями; отдельного факта заслуживают только отклонения и циклы.
**Без среза агент:** создаёт циклы между модулями, размазывает логику через границы.
**Диаграмма:** flowchart зависимостей; циклы — отдельным фактом-предупреждением.

## 2. `event-graph` — граф событий · ★★★★☆ · S–M

**Что:** кто продюсит какие события, кто консюмит, и семантика доставки.
**Реально извлечь:** publish-вызовы с литеральными топиками, подписки/хендлеры, конвеншн-роутинг
по типу сообщения (MassTransit/NServiceBus), схемы из registry-файлов. Консюмеры вне репо —
не видны (граница видимости).
**Как извлекать.** Два подтипа, определи в разведке:
- *брокерные*: publish/emit/produce ↔ subscribe/consume/handler; топики из конфигов брокера;
  схемы (avro/proto/json-schema) как атрибуты; outbox-таблицы в миграциях; AsyncAPI-файлы;
- *in-process*: grep по publish даёт мусор — источник истины в DI-регистрациях подписчиков
  (`AddSingleton<ISubscriber<T>>`, MediatR-хендлеры) и в коде диспетчера.
**Обязательный факт среза — семантика доставки**: sync/async, порядок, поведение при сбое
подписчика (валит ли бизнес-операцию). Это то, что агент без памяти нарушит.
**Ломает:** имена топиков из env/конфига, CDC/Debezium (publish-вызова в коде нет вообще),
retry/DLQ-топология.
**Без среза агент:** меняет payload события, не зная потребителей; забывает уведомить консюмера.
**Диаграмма:** flowchart «продюсер → событие → консюмеры», одна на срез/домен.

## 3. `data-ownership` — данные и владение · ★★★★☆ · M

**Что:** таблицы/коллекции, владельцы, чужие доступы; крупнозернистый data flow (кто читает/пишет
какое хранилище) — тоже сюда.
**Реально извлечь:** таблицы, колонки, объявленные FK, историю схемы (git blame миграций),
ORM-маппинг код↔таблица. **Неявные FK** (constraints не ставят под нагрузкой) — только `inferred`
из JOIN-ов и именования: гипотеза, не факт. Field-level lineage — только при dbt/декларативных
ETL в репо, иначе не пытайся.
**Как извлекать:** миграции и модели → владелец; GRANT-ы в миграциях/terraform; поиск обращений
к таблице из чужих модулей — каждое такое обращение отдельный факт (будущие грабли).
**Ломает:** raw SQL/Dapper (схема фрагментами), NoSQL/JSONB (структура известна только коду),
миграции вне репо, shared database (граф есть — смысла мало).
**Без среза агент:** пишет миграцию, ломающую неявную связь; «чинит» данные в чужой read-model.
**Диаграмма:** группировка таблиц по владельцам, красные стрелки чужих доступов.

## 4. `api-contracts` — контракты API · ★★★★☆ · M (провайдер ★★★★★, потребители ★★★☆☆)

**Что:** endpoints, назначение, известные потребители.
**Реально извлечь:** провайдер-сторона с file:line — роуты, gRPC из proto, GraphQL-схемы,
auth-атрибуты, версии. Потребители — только внутрирепозиторные клиенты, сгенерированные клиенты
(Refit/NSwag/protoc = факт потребления) и contract-тесты (лучший источник!). Недекларированные
внешние потребители из кода не видны никогда — фиксируй границу видимости.
**Как извлекать:** сначала **готовые контракты** — openapi/proto/graphql, `specs/`, `contracts/`
(contract-first кодогенерит роутинг — grep по `[HttpGet]`/`MapGet` даст ноль; есть спеки →
стоимость падает до S). Нет — fallback: роуты/контроллеры/атрибуты. Закоммиченный руками swagger
может дрейфовать от фактических роутов — сверяй оба, расхождение = отдельный факт.
**Ломает:** контракт в отдельном репо/registry, динамический роутинг (маршруты из БД),
API-gateway-маршрутизация вне репо.
**Без среза агент:** «чинит» endpoint, ломая неизвестных потребителей; путает публичный контракт
с внутренним.
**Диаграмма:** таблица endpoints по модулям + flowchart потребителей для критичных.

## 5. `external-integrations` — внешние системы и контейнеры · ★★★★☆ · S

**Что:** внешние системы (платёжки, CRM…), направление и точка интеграции; сюда же
container-уровень — БД, брокеры, кэши сервиса. При наличии IaC в репо — и деплой-топология
(реплики, ingress, различия окружений).
**Реально извлечь:** SDK в зависимостях (`StackExchange.Redis` = есть Redis), внешние URL в
конфигах, compose/Helm/K8s/Terraform — там контейнеры и связки `declared` буквально;
`values-{env}` диффы = поведение по окружениям.
**Ломает:** полирепо/infra-репозиторий (деплой уходит за горизонт — честно пиши «деплой определён
вне репозитория»), секреты и адреса только в Vault/CI, sidecar/mesh-маршрутизация.
**Без среза агент:** не знает, что «функция» пересекает сетевую границу — предлагает транзакцию
поверх двух сервисов; предлагает in-memory state при 12 репликах.
**Диаграмма:** система в центре, внешние по краям, направление стрелок = кто кого вызывает.

## 6. `invariants` — инварианты и ограничения · ★★★☆☆ · L

**Что:** бизнес-правила в коде: «заказ нельзя отменить после отгрузки», идемпотентность.
**Реально извлечь:** формализованные — DB-constraints, валидаторы, guard-клаузы (`declared`/
`observed`, можно авто-подтверждать при high). Выведенные из имён тестов и комментариев —
`inferred`-гипотезы: отличить намеренный инвариант от случайного текущего поведения агент
не может, это человеческая голова.
**Как извлекать:** констрейнты в миграциях, валидаторы, доменные исключения с текстом
(само-документация), **имена тестов** (`test_cannot_cancel_shipped_order` — инвариант, записанный
человеком), комментарии с «нельзя/должен/всегда/никогда».
**Ломает:** инварианты, живущие только дисциплиной команды; распределённые между сервисами.
**Без среза агент:** делает изменения, которые компилируются и проходят типы — и ломают домен.
Самый ценный срез каталога.
**Диаграмма:** не рисуется — список по модулям, сгруппированный по сущностям.

## 7. `config-flags` — конфигурация, меняющая поведение · ★★★★☆ · S

**Что:** всё, что переключает поведение: фичефлаги — частный случай; Options-классы, per-env
оверрайды, env-переменные, лимиты.
**Реально извлечь:** точки чтения конфига с file:line, дефолты, диффы окружений, ветвления по
флагу; мёртвые флаги (объявлен — не читается). *Актуальные значения* флагов из
LaunchDarkly/Unleash/БД — не извлекаемы: пиши «значение определяется вне репо».
**Как извлекать:** реестр флагов/Options + поиск мест ветвления; отдельно — различия per-env.
Ветвление в библиотеке вне репо → `confidence: low` с пометкой «branch point вне репо».
**Без среза агент:** тестирует один режим поведения из четырёх и уверенно говорит «работает»;
«чинит» выключенный код.
**Диаграмма:** таблица флаг/опция → что переключает → где ветвится.

## 8. `gotchas` — грабли и workarounds · ★★☆☆☆ · M (ценность высокая, точность низкая)

**Что:** флакающие тесты, обязательный порядок вызовов, «не трогай — так надо», причины ревертов.
**Реально извлечь:** сигналы «здесь кто-то обжигался» — каждый честен, но *почему* —
восстанавливается плохо. **Весь срез — только гипотезы** с обязательной ссылкой на сигнал
(коммит/строка): тогда ложные срабатывания дёшево отсеиваются человеком на ревью. Не
авто-подтверждать.
**Как извлекать:** TODO/HACK/FIXME/WARNING и локализованные аналоги («не трогать», «важно»);
предупреждающие doc-комментарии; **ADR и docs-каталоги** (в дисциплинированных репо грабли живут
там); revert- и hotfix-коммиты в `git log`; аномальный churn; отключённые тесты с комментариями.
В «чистом» репо срез тонкий — это нормально; основной прирост идёт от актуализации после задач.
**Без среза агент:** повторяет ошибки, откат которых уже стоил инцидента.
**Диаграмма:** не рисуется — лента по модулям, свежие сверху.

## Условные срезы — предлагай только при явных артефактах в репо

## 9. `state-machine` — статусы и переходы · ★★☆☆☆, при SM-артефактах ★★★★☆ · S–M

Есть SM-библиотека (Stateless, XState, Spring StateMachine), валидатор переходов или тесты на
переходы → состояния и переходы читаются буквально, извлекай как факты. Есть только status-enum →
список состояний ★★★★★, но переходы — перечисление наблюдаемых присваиваний (`inferred`-гипотеза
с диаграммой на валидацию); запрещённые переходы из кода не видны. Ломает: статус, меняемый raw
SQL/админкой; переходы, распределённые между сервисами. Без среза агент добавляет переход,
невозможный в домене. **Диаграмма:** stateDiagram; гипотетические переходы — пунктиром.

## 10. `workflow` (BPMN/saga) — оркестрированные процессы · ★☆☆☆☆, при артефактах ★★★★★ · S

Только если в репо есть `*.bpmn`/`*.dmn`, Temporal/Cadence-workflow, Durable Functions, саги
(MassTransit), Airflow DAGs, Step Functions — процесс буквально записан, извлекается чтением,
включая привязку service task → код воркера. Нет артефактов → **не предлагай и не строй гипотез**:
из кода видна только автоматизированная тень процесса. Без среза агент меняет шаг саги, не
понимая компенсаций.

## 11. `context-map` (DDD) — границы контекстов · ★★☆☆☆ · M — всегда только гипотеза

Агент строит **черновик** карты: кластеры модулей, CODEOWNERS (границы команд ≈ границы контекстов
по Конвею), дублирование сущностей (`Customer` в двух модулях с разными полями = признак двух
контекстов), ACL-мапперы на границах, отдельные схемы БД. Тип отношений (Conformist/ACL/Shared
Kernel — намеренно?) из кода не восстанавливается. Все факты — `inferred`, весь срез проходит
ревью человеком; есть ADR с именами контекстов → повышай до факта. Ценность: человек правит
черновик за полчаса вместо дня воркшопа; агент перестаёт переиспользовать сущность чужого
контекста «потому что похожа».

## Что каталог сознательно НЕ хранит

- **Sequence-диаграммы** — не хранимый срез, а **операция по запросу** («трассируй сценарий X»):
  сценариев бесконечно много, выбор важных — человеческое знание. Агент трассирует хорошо (через
  DI и интерфейсы «по смыслу»), но рвётся на границе брокера. Хранить стоит максимум 3–5 трасс
  ключевых бизнес-операций, найденных по интеграционным тестам, — как факты соответствующих срезов.
- **Capability map** — выкинут: бизнес-способности — язык стратегии, не кода. Единственный вид,
  где даже режим гипотез вреден — убедительные выдумки при нулевой проверяемости.
- **BPMN без артефактов** — см. `workflow`.
