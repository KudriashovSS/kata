# Прототип: база технических фактов о проекте

Инвертируем задачу системного анализа: не проектируем схему знаний заранее и не предсказываем
будущее — агент **реверс-инжинирит технические факты из уже существующего кода**, человек только
выбирает нужные срезы и подтверждает результат. Дальше эта память живёт рядом с проектом,
актуализируется при каждой задаче и (гипотеза) делает будущие реализации качественнее и дешевле.

Наша работа = **хороший скилл + честные эвалы**. Всё остальное делает фронтир-модель на вайбе.

## Как это выглядит для пользователя

1. Ставит скилл `tech-facts` и говорит агенту: «построй базу технических фактов о проекте».
2. Агент разведывает репозиторий и поднимает локальный **picker** (см. [references/picker.html](skills/tech-facts/references/picker.html)) —
   красивую страницу со срезами, которые реально есть в этом проекте: event graph, модульные
   зависимости, владение данными, контракты, инварианты, грабли…
3. Пользователь отмечает нужное. Можно выбрать один срез («мне достаточно Event graph») —
   пользователя в тиски не зажимаем. В тиски зажимается агент: всё, что он извлёк, обязано лечь
   в реляционную схему с evidence.
4. Агент извлекает факты и генерирует **вьювер** (см. [references/viewer.html](skills/tech-facts/references/viewer.html)) —
   по странице на срез: человекопонятная диаграмма (а не сырой UML), карточки фактов с evidence и
   confidence. Человек принимает, отклоняет и **комментирует** факты прямо на странице; ревью
   возвращается агенту и применяется к памяти.
5. После ревью — сохранение в **xmemory** (первичное хранилище: агент сам придумывает схему под
   выбранные срезы, она дорастает при добавлении новых; файловый `.tech-facts/` — fallback).
   Вьювер остаётся витриной для человека: перегенерируется из памяти в любой момент.
6. В будущей разработке любой агент перед задачей читает из xmemory релевантные факты (вместе с
   комментариями человека), после задачи — актуализирует их. Каждое чтение и запись логируются:
   видно, какой факт в какую задачу попал.

Так у памяти два потребителя: **человек понимает систему через HTML-вьюверы, агенты через xmemory
решают задачи правильно с первого раза**.

## Как это закрывает требования хакатона

- **Поток задач** — реальные задачи разработки в целевом репозитории (и реплей его истории в эвалах).
- **Цикл «выполнил → оценил → извлёк урок»** — задача выполнена → реальность кода сверена с памятью →
  расхождения становятся новыми candidate-фактами / пометками stale.
- **Уроки меняют поведение** — следующий агент читает обновлённые active-факты перед задачей.
- **Память переживает рестарты** — внешнее хранилище (xmemory / файлы в репо), каждый запуск агента —
  новый процесс.
- **Дельта чистая/обученная** — измеряется реплеем истории: [evals/README.md](evals/README.md).
- **Устаревание, противоречия, HITL, observability** — встроены в жизненный цикл факта
  (candidate → active → stale) и журналы MemoryRead/MemoryWrite, см. протокол памяти.

## Полевой тест

Скилл прогнан на реальном рабочем репозитории (services-platform, contract-first .NET): извлечено
37 фактов по 4 срезам, все прошли ревью. Тест дал 13 конкретных доработок каталога и протокола
(contract-first извлечение api-contracts, in-process события + семантика доставки, локализованные
маркеры и ADR как источник gotchas, Options-классы как config-flags, анти-шум module-graph,
гранулярность сущностей, префиксы id) — все внесены в текущую версию файлов.

Вторая итерация перенесла память в живой xmemory-инстанс: цепочка «факт → ревью → задача»
достаётся обходом графа, семантическая выборка агентского вида работает (на «собираюсь добавить
доменное событие» первым приходит факт о семантике доставки). Ещё 10 доработок внесены: стабильные
первичные ключи в схеме, журналы только с явными id (иначе xmemory рождает объекты-призраки),
готовое описание для `xmd generate`, обязательная верификация после переноса, порционное ревью
по срезам, вьювер с защитой от потерянных фактов, `facts.json` вместо подстановки в HTML,
показ human_notes.

## Что попробовать дальше

1. Собрать первый эвал: выбрать реперный коммит, одну «фичу из будущего», написать к ней 5–10
   архитектурных проверок.
2. Подключить xmemory-адаптер, когда будет доступ к инстансу (до этого работает файловый),
   и смигрировать в него память полевого теста.
3. Погонять режим использования: реальная задача в services-platform с чтением фактов из памяти.
