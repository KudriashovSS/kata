# Заметки по проекту Системного анализа

## Цель проекта

Агенты без структурированной памяти уже могут справлятся с задачами указанными в проекте используя статический контекст проекта (спеки, код и тп). Цели проекта - 
* не добавить абсолютно новых функционал, а оптимизировать и улучшить работу знаниями о проекте через их структурированное хранение. Отделить представление (документы проекта) от данных (реальные факты). Уменьшить деградацию знаний о проекте по мере роста фактов и нарастания изменений.
* добавить цикл самоулучшения сбора фактов через агентский цикл сбора правил работы с проектом.

## Автоматизируемый процесс

* источник фактов
* агент вычлиняет факт используя правила работы и другие факты из памяти, записывает ввиде json патча в хранилище.
* отдельный агент валидирует собранные факты или изменения существующих
  * если замечения есть, то формируется цикл доработки
    * отдельный агент анализирует корневую причину нарушения, записывает ее в draft rules.
      * если ее нет, то blocked.
    * перезапускает вычлинение факта заново + с директивой использовать новое draft rule.
    * после перегенерации переходим к валидации результата, если проблема устраненна и замечаний нет, то draft rule включается в MR для одобрения человеком. если нет, то цикл повторяется.
  * если к фактам нет замечаний, то формируется MR на человека для финальной проверки.
  * если есть замечания с MR от человека, то запускается цикл доработки с правилом полученным от человека.

* использование xmemory для структурированного хранения фактов о разрабатываемой Системе полученных в результате Системного анализа. Для каждого факта разрабатывается своя схема с атрибутами, факты связаны между собой.
  * цели
  * не цели
  * глоссарий
  * бизнес требования
  * нефункциональные требования
  * роли
  * сценарии
  * эпики
  * истории
  * бизнес сущности
  * аттрибуты бизнес сущностей
  * связи между фактами
* xmemory xранит факты о PRD, АДР, Use Case, спецификациях на разработку.
* формирование фактов проекта с помощью LLM из входящих источников
  * готовые спеки
  * обсуждения команды
  * обсуждение с заказчиком
* запись xmemory новых или измененных фактов, деактивация неактуальных.
* чтение агентом из xmemory фактов о проекте при формировании документации, ответов на вопросы по Системе
* проверка конфликтующих, дублирующих фактов между собой
* добавление к фактам атрибутов. как пример у разных сущностей могут быть:
  * даты внесения
  * автора
  * актуальности
  * чем заменена
* факты на каждом уровне абстракции должны быть не протеворечивы, то есть факты требования не могут нарушать факты цели или существовать без верхнеуровневых требований.
* для каждого факта должна хранится информация откуда он был получен (название мероприятия, название документа, ссылка на статью и тп)

## Результаты проверки MVP

### Итог

Узкий вертикальный MVP выполним. Текущий MVP 0 перегружен: в нем одновременно объединены хранилище знаний, извлечение фактов, поиск семантических конфликтов, генерация PRD, Git/MR workflow и самоизменяющиеся правила агента. Для хакатона сначала нужно доказать пользу структурированной памяти проекта, а обучение правил вынести в следующую фазу.

Главная проверяемая гипотеза: при внесении изменений в растущий PRD агент со структурированной памятью реже пропускает связанные требования, использует устаревшие сведения и создает противоречия, чем тот же агент, работающий только с документами и git history.

### Блокирующие решения до реализации

1. Определить источник истины. Рекомендуемый вариант для MVP:
   * одобренные структурированные факты в Git (JSON или JSONL) — canonical state;
   * xmemory — перестраиваемый индекс для extraction, relations и retrieval;
   * PRD — детерминированная проекция текущего snapshot фактов.
2. Разделить утверждение источника, кандидата и одобренный факт. Требование становится знанием проекта только после проверки и одобрения человеком.
3. Устранить противоречие scope: если проверяются связи требований с целями, минимальный тип `Goal` должен присутствовать хотя бы как read-only seed. Внешние встречи и обсуждения в MVP не входят.
4. Запретить запись кандидатов в canonical memory до валидации и merge. Отклоненный MR не должен оставлять побочных изменений.
5. Формализовать идентичность, версии, provenance, допустимые переходы состояния и конкурентные изменения.
6. Определить разные результаты проверки: `noop_duplicate`, `supersede`, `needs_human`, `reject_invalid`. Конфликтующий кандидат нельзя молча терять.
7. Ограничить цикл доработки одной повторной попыткой. Затем результат переводится в `needs_human` с диагностикой.
8. Считать содержимое внешних документов недоверенными данными. Инструкции внутри источника не должны менять правила агента или разрешать вызов инструментов.

### Рекомендуемый MVP 0

Scope:

* один репозиторий, один язык и один фиксированный Markdown-шаблон PRD;
* один изменяемый тип факта — `BusinessRequirement`;
* цели загружаются заранее и доступны только для чтения;
* один CLI-orchestrator вместо отдельного MCP и нескольких сервисов;
* человек одобряет change set через MR;
* xmemory синхронизируется только после merge и может быть полностью пересобрана из Git;
* динамические rules/skills, ADR, Use Case, NFR, роли, бизнес-сущности, произвольный Q&A и внешние обсуждения отложены.

Workflow:

```text
PRD или change request @ commit
  -> extraction preview без записи
  -> candidate change set
  -> детерминированные gates
  -> семантическая проверка с evidence
  -> accept | revise | needs_human
  -> MR и решение человека
  -> merge
  -> idempotent sync в xmemory
  -> deterministic render PRD / retrieval
```

Отдельные агенты для extraction, validation и root-cause в MVP не нужны. Достаточно трех изолированных этапов одного orchestrator. Семантический валидатор только формирует finding; окончательное решение о конфликте или замене принимает человек.

### Минимальная модель

```text
Goal
  id
  text

RequirementRevision
  fact_id                 # неизменяемый внутренний идентификатор
  display_id              # например, FR-1
  revision
  text
  goal_ids
  state                   # candidate | active | superseded | rejected
  supersedes?
  source_uri
  source_revision         # commit, message id или version
  source_anchor           # section, line range или timestamp
  source_digest
  source_author
  extracted_by
  approved_by?

ChangeSet
  id
  base_snapshot
  idempotency_key
  operations[]            # add | supersede | retire
  findings[]
  status                  # proposed | validated | approved | rejected | merged
```

`FR-1` не должен использоваться как внутренний primary key: номер может измениться или отсутствовать во входном тексте. Для истории используется стабильный `fact_id`, а каждая правка создает immutable revision.

Минимальные инварианты:

* у требования не более одной активной ревизии;
* активная ревизия одобрена и имеет проверяемый source;
* повторный импорт того же source revision дает пустой patch;
* замена атомарно создает новую ревизию и переводит старую в `superseded`;
* hard delete запрещен, откат оформляется новым change set;
* открытый blocking finding запрещает merge, но не уничтожает кандидата и evidence;
* изменение `base_snapshot` требует повторной валидации;
* сгенерированный PRD помечается как derived и повторно не импортируется как независимый источник.

### Границы валидатора

Детерминированные gates проверяют:

* схему, обязательные поля и типы;
* уникальность ID и idempotency key;
* существование ссылок на цели;
* допустимый переход lifecycle;
* наличие provenance;
* единственность активной ревизии;
* отсутствие циклов `supersedes`;
* соответствие `base_snapshot` текущему состоянию.

LLM может только предложить findings о возможном семантическом дубле или конфликте. Такие выводы должны содержать участвующие fact IDs, source fragments и объяснение. Автоматически запрещать или заменять факт по одному LLM-решению нельзя.

### Правила самоулучшения

Память правил процесса и память фактов проекта имеют разный trust level и lifecycle, поэтому их нельзя изменять одним решением. Замечание человека сначала становится validation issue или regression fixture. Draft rule создается только для повторяемой ошибки процесса и продвигается отдельно, если:

* исправлен исходный пример;
* проходят скрытые аналогичные примеры;
* не сломана короткая regression suite;
* человек одобрил текст и scope правила.

Этот контур не входит в MVP 0.

### Evaluations

Byte-to-byte совпадение произвольно сгенерированного текста после round trip не является полезной метрикой: LLM недетерминирована, а одинаковая формулировка не доказывает корректность памяти. Такое совпадение допустимо требовать только от детерминированного шаблонного renderer.

Минимальный набор состоит из 8-12 заранее размеченных change requests:

* корректное добавление;
* точный дубль;
* семантический дубль;
* явная замена;
* деактивация;
* конфликт с целью;
* конфликт с требованием в другом месте;
* неоднозначное изменение с ожидаемым `needs_human`.

Baseline и memory-вариант запускаются на одном commit с одинаковыми моделью, базовыми инструкциями, инструментами и бюджетами. Перед каждым кейсом восстанавливаются Git и memory snapshot; желательно выполнить не менее трех запусков на кейс.

Primary metric — доля полностью корректных задач: правильный набор операций, правильный verdict и отсутствие unsupported facts. Дополнительно измеряются extraction precision/recall, conflict precision/recall, stale-fact leakage, корректность provenance, число человеческих исправлений, tokens, latency и стоимость первоначального наполнения памяти.

Обучение правил оценивается отдельным pre/post экспериментом на held-out примерах, иначе нельзя определить, что именно дало улучшение: память проекта или изменение поведения агента.

### Проверка применимости xmemory

По актуальной документации xmemory поддерживает XMD-схемы, primary/composite keys, relations, предварительный `/extract` без записи, детерминированные `structured_mutations`, структурированное чтение и несколько instances. Этого достаточно для предложенного вертикального среза:

* [XMD schema format](https://xmemory.ai/xmd/)
* [REST API](https://xmemory.ai/api/)

Перед реализацией нужен короткий spike:

1. создать instance и провалидировать XMD-схему;
2. выполнить extraction preview;
3. применить structured mutations и проверить идемпотентность;
4. прочитать факты в structured mode;
5. пересоздать отдельный instance из Git fixtures;
6. проверить доступность structured writes, quotas и latency.

Нельзя заранее рассчитывать на Git-подобные возможности xmemory: в XMD v1 нет атрибутов у relations, откат committed schema migration не поддерживается, а data clone/snapshot/export публично не документированы. Поэтому branch, rollback и воспроизводимость эксперимента в MVP обеспечивает Git, а не удаленное хранилище.

### Критерий готовности MVP 0

MVP готов, если на зафиксированном наборе change requests он воспроизводимо:

* извлекает ожидаемые требования и точный provenance;
* не изменяет canonical state до человеческого одобрения;
* повторно применяет одобренный change set без дублей;
* корректно выполняет add, supersede, retire и noop;
* не выдает superseded или rejected факты как актуальные;
* генерирует PRD, содержащий каждый активный факт ровно один раз и не содержащий неподтвержденных утверждений;
* показывает заранее зафиксированное улучшение primary metric относительно baseline.
